# マルチプレイ化の設計レビューと計画

現在の構成を読み解き、設計上の良い点と課題を整理したうえで、LAN内の同時プレイからインターネット公開、さらにMMO規模へ進めるための段階的な計画をまとめます。コードの構成は [アーキテクチャ](ARCHITECTURE.md)、現在の仕様は [ゲームの仕様](game-spec.md) を参照してください。

## 要約

- このリポジトリは「ソロ専用ゲーム」ではなく、**サーバー権威型マルチプレイのゲームコアを、ブラウザーWorker・Node・Cloudflare Durable Objectの3つの実行環境で動かしている**構成です。ソロプレイは同じコアを `playerLimit: 1` でWorker内に閉じ込めたものです(`infrastructure/browser/solo-runtime.mts`)。
- 「LANで仲間と遊ぶ」入口は止めてあるだけです。クライアントの `loadMultiplayerConfig()` が `online` を強制的に `solo` に落とし(`src/multiplayer-config.ts`)、`pnpm start` のサーバーは接続設定ファイルを配信しないため、`HOST=0.0.0.0` にしてもソロのままです。
- インターネット公開とMMO規模化に向けた最大の技術負債は通信量です。5人の部屋でも1クライアントあたり約218 KB/s(約1.7 Mbps)を受信し、20人では約400 KB/s、サーバー送信合計は約8 MB/sになります。全員に全量スナップショットを約10 Hzで送る方式が原因です。
- 進め方は4段階にします。**Phase 0: LANの入口を開けつつ、後から変えると再設計になる4つの骨格を決める** → **Phase 1: 配信最適化と予測の一般化** → **Phase 2: インターネット公開** → **Phase 3: 並列インスタンスによる規模拡大**。継ぎ目のない1つの世界への分割は、需要が見えてから別途判断します。

## 現状のアーキテクチャ

```
                 +------------------- application/game-core.mts -------------------+
                 |  rooms / connect() / tick() / exportState() / importState()      |
                 |  decodeCommand (protocol.mts) -> actions.mts -> shared/* ルール   |
                 +---------+----------------------+----------------------+---------+
                           |                      |                      |
   infrastructure/browser  |     server.mts       |    cloudflare/        |
   solo-worker + IndexedDB |  Node http + ws      |  Durable Object      |
   (playerLimit 1, SOLO)   |  world.json 10秒毎   |  SQLite checkpoint    |
   ← 現在の公開形態        |  LAN/展示/検証用     |  SERVICE_ENABLED=false|
```

| 観点 | 実態 |
| --- | --- |
| 権威 | サーバー(コア)がすべて決定。クライアントは `move(dx,dz)` と `action` を送るだけで、座標・ダメージ・持ち物を送れない |
| tick | 50 ms。状態ブロードキャストは90 ms間隔+イベント発生時(全量JSON) |
| 接続 | WebSocket、テキストJSON、`maxPayload 2048`、圧縮なし |
| 再接続 | `session` トークンで120秒(Node)/7日(Cloudflare)/無期限(ソロ)再開。同一セッションの再接続で旧ソケットを置換 |
| 保存形式 | 3環境とも `exportState()` の同一JSON(`version: 1`, `worldVersion: 4`)。部屋ごとに `sessions` としてプレイヤー進行を内包 |
| 部屋 | 名前は英数20文字、`playerLimit` 既定5(`WORLD.maxPlayers`)、コアの上限64 |
| 既存のマルチ実績 | 展示モード(2台のPCが各自のlocalhostからゲームを読み込み、1台のNodeサーバーに `ws://` で接続)。`tests/exhibition-lan.test.mjs` で再現 |
| クライアント予測 | `src/local-prediction.ts` にあるが `mode === 'lan'` のときのみ有効。他プレイヤーは指数追従で補間 |

### 計測

`dist/application/game-core.mjs` にダミーの `GameConnection` を5体/20体接続し、200 tick(50 ms間隔)の間、全員に走る `move` を送り続け、各ソケットの受信バイト数と `tick()` の処理時間を集計しました(Node 22、`EMBER` 部屋)。実ネットワークの往復遅延や描画負荷は含みません。

| 人数 | 軽量スナップショット | 全量スナップショット | 1クライアント受信 | サーバー送信合計 | tick平均 | 保存JSON |
| --- | --- | --- | --- | --- | --- | --- |
| 5 | 20.9 KB | 29.6 KB | 約9.6 msg/s, 218 KB/s | 1.1 MB/s | 0.50 ms | 42.5 KB |
| 20 | 39.5 KB | 48.2 KB | 約9.4 msg/s, 398 KB/s | 8.0 MB/s | 0.85 ms | 42.8 KB |

軽量スナップショット20.9 KBの内訳は、`enemies` 14.0 KB(34体、ほぼ烏の城)、`players` 6.3 KB、`animals` 0.4 KBです。動いていない敵の全情報が毎回送られているのが支配的で、CPUは十分に軽く、ボトルネックは帯域とシリアライズ回数です。

## 設計上好ましい点

1. **ドメイン中心のレイヤー分離が機能している。** `shared/`(ルール) ← `application/`(調停) ← `infrastructure/`・`cloudflare/`・`src/`(環境)の依存方向を `scripts/check-architecture.mjs` が強制し、ドメインからブラウザー/Nodeのグローバルを排除している。同じコアがWorker・Node・Durable Objectで無修正で動く。
2. **ソロとマルチのロジック差分がゼロ。** マルチ化で「ソロで動いていた挙動がオンラインで変わる」種類の不具合が構造的に起きにくい。
3. **最初からサーバー権威・不信クライアント前提。** `decodeCommand` が未知JSONを判別共用体に変換し、クライアント発のダメージ/座標/IDを捨てる。行動側は距離・視線・コスト・クールダウン・トークンバケット(70個、35個/秒補充)で検査する。
4. **接続ポート(`GameConnection`)の抽象化が薄くて正しい。** `ws`、Cloudflareの `WebSocket`、Workerの `postMessage` を同じ `on/send/close/ping` で扱い、テストはダミーソケットで中身まで検証できる。
5. **バックプレッシャーと復旧の配慮。** `bufferedAmount ≥ 512 KB` のクライアントには送信を止め `needsWorld` を立てて次回に全量を送る。再接続時のセッション置換、乗り物・運搬・交換の解除、安全なスポーン探索まで揃っている。
6. **保存の堅牢性。** 原子的置換、バックアップ世代、SHA-256検証、ループバックポートによる二重起動防止、破損ファイルの退避、保存先が配信ディレクトリ外であることの検査。Cloudflare側は保存成功までメッセージをキューに留める。
7. **ネットワーク境界のデフォルトが安全。** 既定はループバックのみ、Host/Originの検査、`maxPayload 2048`、WebSocketパスの限定、展示モードではビルドIDの一致を要求。
8. **部屋ごとのルール(`RoomRules`)が既にある。** 「家庭用」「公開用」ルールを追加しやすい。
9. **テストが実通信で書かれている。** 5クライアント同期・6人目拒否・部屋分離・再接続・権威チェックが `ws` で実際に接続して検証されている。
10. **運用上の情報。** `/api/health` で人数・バージョン・保存状態を返し、ワールドデータは `shared/*-baked.mts` に焼き込み済みで起動が軽い。

## 課題

### 通信方式(最優先)

| # | 課題 | 根拠 | 影響 |
| --- | --- | --- | --- |
| A1 | 全量スナップショットを全員に約10 Hzで送る | `game-core.mts` `tick()` 末尾の `broadcast(room, snapshot(room))`。行動のたびに `snapshot(room, true)` を全員に送る(`actions.mts`) | 帯域が人数の2乗で増える。モバイル回線・無料ホスティングで不成立 |
| A2 | 興味領域(AOI)がない | 世界は4,096 × 2,048 mだが、遠方の個体も全員に送る | 人数が増えるほど無駄が線形に増える |
| A3 | 差分がない。変化していない敵・資源も毎回 | `enemies` が21 KB中14 KB | 最も簡単に削れる部分 |
| A4 | 圧縮なし(`perMessageDeflate: false`) | `server.mts` | JSONは圧縮率が高く、有効化だけで大きく削減できる見込み(CPUとのトレードオフ) |
| A5 | シリアライズの重複 | `adventure` を `JSON.parse(JSON.stringify())`、`gulf` を `structuredClone` で毎回コピー | 差分化すれば消える |

### クライアント予測・補間

| # | 課題 | 根拠 |
| --- | --- | --- |
| B1 | 予測は `lan` モードのみ有効。`online` では自分の移動もサーバー往復待ち | `src/main.ts` の `renderer.prediction.enabled` |
| B2 | 入力にシーケンス番号がなく、`state` に「どの入力まで処理したか」がない。再調停は時間(250 ms)とRTT/2の推定に依存 | `protocol.mts` `move`、`local-prediction.ts` |
| B3 | 他プレイヤーはスナップショット到着時の座標へ指数追従。遅延バッファがなく、ジッターで速度が揺れる | `world3d.ts` |
| B4 | 移動入力の送信頻度が `lan` では毎フレームで、サーバーのトークンバケット(35/秒)と整合しない | `main.ts`、`game-core.mts` |

### アイデンティティ・セキュリティ

| # | 課題 | 根拠 |
| --- | --- | --- |
| C1 | 本人性がない。名前は自由文字列、`session` トークンは再開用の合言葉であって認証ではない | `connect()` の `name` 処理 |
| C2 | セッショントークンをURLクエリで送っている | `multiplayerUrl()` |
| C3 | チャットのモデレーション(NGワード、ミュート、通報、ブロック)がない | `chat` は長さ制限とクールダウンのみ |
| C4 | IPあたりの接続数制限、部屋作成の制限がない(Node) | `server.mts` |
| C5 | `HOST=0.0.0.0` は信頼できるLAN限定。TLSなしでの公開は想定外 | `DEVELOPMENT.md` |

### 永続化とデータモデル

| # | 課題 | 根拠 |
| --- | --- | --- |
| D1 | プレイヤーの進行が「部屋」に属している。部屋をまたいで同じキャラを使えず、ソロ(IndexedDB)とオンライン(サーバー)も別の保存 | `exportState()`、`solo-save.mts` |
| D2 | 全部屋をまとめた1つのJSONを10秒ごとに全量書き出し | `local-save.mts` |
| D3 | 世界バージョン移行のコードが `importState` 内に蓄積し、版ごとの移行関数列になっていない | `game-core.mts` |
| D4 | 保存セッション上限100(Cloudflare)、サイズ上限1.5 MB | `worker.mts` |

### ホスティング・運用

| # | 課題 | 根拠 |
| --- | --- | --- |
| E1 | Durable Object実装は50 ms常時tickで、課金単位や休止(Hibernatable WebSocket)と相性が悪い | `worker.mts` |
| E2 | 1部屋(`EMBER`)・5人固定 | `request-handler.mts` |
| E3 | メトリクス・ログの集約がない | `wrangler.jsonc` |
| E4 | 待機切断が30秒固定。家庭内では体験を損なう | `shared/player-inactivity.mts` |

### コード品質

- `src/main.ts` と `src/world3d.ts` にUI・通信・状態管理・描画が集中。通信層を独立モジュールに切り出す必要がある。
- `tsconfig.json` は `strict: false`。`room`・`player` は型がない。`Room`/`Player` 型を `shared/types.mts` に定義して段階的に広げる。

## 後回しにすると再設計になる決定

スケーリングの課題は「実装は後でよいが、決定は今しないと再設計になる」ものと、「追加的な変更で済む」ものに分かれます。前者はPhase 0で決めます。

| 項目 | 何が固まってしまうか | 決定 |
| --- | --- | --- |
| プレイヤー進行が部屋に属するデータモデル | 保存形式、`player.id` の意味、仲間・交換・地図ピン・運搬が参照するIDの全部 | **進行はプレイヤーに、世界は部屋に。** 現在の保存利用者はソロのIndexedDBだけなので、形式を変える費用が最も安いのは今。ソロ進行を部屋の `sessions` へ取り込むAPIは、古いモデルを固定化するため採らない |
| プレイヤーの識別子 | 接続ごとの乱数UUIDが `player.id` になっており、後から「人」の識別子に差し替えると参照箇所を全部触る | ブラウザーが生成した鍵のハッシュを `player.id` にする。LANでは署名を検証せず、インターネット版で検証を足す |
| クライアントの「state は世界の全量」という前提 | `setState` が全置換、`state.players.find` が各所、AOI外の個体の消え方が未定義 | `src/` に部分更新と削除を受け付けるエンティティストアを置き、以後の機能はそれ経由で書く。中身は当面全量のまま |
| 行動側の `broadcast(room, snapshot(room, true))`(約40か所) | 差分配信への切り替えで全箇所を触る | 「部屋を汚れ扱いにする」APIに置き換え、送信は tick 側の1か所に集約 |
| プロトコルの形 | `welcome` に版がなく、トークンがURLにある。テストや展示ツールが依存 | `protocolVersion` を入れ、トークンは接続後の最初のメッセージで送る |

後回しで問題ないもの: 差分配信・AOI・圧縮の実装そのもの、入力の連番と確認応答、モデレーション、接続数制限、メトリクス、ホスティング先の選択(コアがポート経由で動くため、移行費用は永続化アダプターに閉じる)。

継ぎ目のない1つの世界へのゾーン分割だけは、いつ行っても再設計です。`room` が衝突世界・敵・住民・湾を丸ごと持ち、各システムが `room` 全体を引数に取るためです。代わりに「同じ谷の並列インスタンスを複数立て、1インスタンスに数十人」という形なら、現在の構造のまま到達できます。**まず並列インスタンス方式で公開し、継ぎ目のない世界は需要が見えてから判断します。**

## 段階的な計画

### Phase 0: LANの入口と骨格(1〜2週間)

> **実装済み(2026-11)。** 手順は [家やLANでみんなで遊ぶ](lan-play.md)、構成は [アーキテクチャ](ARCHITECTURE.md) を参照してください。計画からの変更点は次のとおりです。
>
> - LANの入口は `HOST` ではなく `CRO_MULTIPLAYER=lan`(`pnpm run start:lan`)で開きます。`HOST=0.0.0.0` だけで部屋を開くと、スマートフォンで画面を確かめる既存の使い方が変わるためです。
> - LANのアドレス(`http://192.168.…`)は安全なコンテキストではなく、WebCryptoとWeb Locksを使えません。識別子は、安全なコンテキストではECDSAの公開鍵、そうでなければランダムな32バイトの秘密にしました。同じ理由で、スマートフォンのLANページではソロを遊べません。
> - ソロのキャラクターは、保存がサイトごとに分かれるため、ファイルの書き出し・読み込みで持ち込みます。同じページでは最後のソロのキャラクターを覚えておき、ファイルなしで選べます。持ち込むのは持ち物・道具・探索の記録で、部屋にまだその人がいないときだけです。
> - 通信層の切り出しは、ハンドシェイクを行う `src/net/game-socket.ts`、受信の適用を担う `src/net/state-store.ts`、識別子の `src/net/identity.ts` までです。再接続とメッセージの分配は `src/main.ts` に残っています。

目標: ホストが1台のPCで `pnpm run start:lan` を実行し、家族・友人がスマホやPCから招待URL(QR)で入って同じ谷を歩ける。あわせて上記の骨格5点を決め、以後の変更を追加的にする。

| 作業 | 場所 | 内容 |
| --- | --- | --- |
| 0-1 | `src/multiplayer-config.ts` | `online` を `solo` に落とす強制を、設定ファイルの明示フラグで解除できるようにする |
| 0-2 | `server.mts` `startServer()` | `HOST` がループバック以外、または `CRO_MULTIPLAYER=lan` のとき `runtimeConfig: { mode: 'online', room }` を `/multiplayer-config.json` として配信 |
| 0-3 | `package.json` | `start:lan` スクリプト。起動ログにLAN URL一覧を表示 |
| 0-4 | `src/main.ts` 招待モーダル | 既存の `/api/network` に加えてQRコード表示 |
| 0-5 | `shared/room-rules.mts` | `idleTimeoutMs`(家庭用は長く、または無効)と `playerLimit` を部屋ルールへ |
| 0-6 | タイトル画面 | 「ひとりで」「みんなで(ホスト/参加)」の入口。参加側は部屋コード入力 |
| 0-7 | 保存形式 | `exportState()` を `players`(進行、識別子で引く)と `rooms`(世界と「誰がどこにいるか」)に分離。ソロ保存も同じ形式へ移行し、ソロのキャラをそのままLANの部屋へ連れて行けるようにする |
| 0-8 | 識別子 | ブラウザー生成鍵のハッシュを `player.id` に。`welcome` に `protocolVersion`。トークンは最初のメッセージで送る |
| 0-9 | `src/` | 通信層を `src/net/` に切り出し、部分更新を受け付けるエンティティストアを置く |
| 0-10 | `application/` | `broadcast(room, snapshot(...))` の呼び出しを汚れフラグAPIに置き換え、送信を tick 側へ集約 |
| 0-11 | `docs/` | 家庭LANの手引き(ファイアウォール、同一Wi-Fi、ホストPCのスリープ無効、保存のバックアップ) |

設計判断: ホストは既存のNodeサーバー。ブラウザーのソロWorkerをホストにしてWebRTCで配る方式は、NAT/シグナリングを自前で持つ必要があり、既存のサーバー・保存・テストを捨てることになるため採らない。LAN内は信頼できるネットワークとみなし、TLSと署名検証は入れない。

### Phase 1: 配信最適化と予測の一般化(2〜4週間)

目標: 1クライアントあたりの受信を20 KB/s以下(現在の約1/10)、自分の移動は即応、他人の移動は滑らか。

| 作業 | 場所 | 内容 |
| --- | --- | --- |
| 1-1 | `application/snapshot.mts`, `game-core.mts` | スナップショットを3種類に分割: `world`(資源・焚き火・村・湾、変化時のみ)、`actors`(変化した個体だけ、10 Hz)、`events`(攻撃・ジャンプ・被弾などの一回限りの出来事) |
| 1-2 | `game-core.mts` | AOI: `shared/spatial-grid.mts` の `PlacementGrid` を動的アクターにも使い、各プレイヤーに半径内の個体だけ送る。購読モデルとして作り、後の並列インスタンスやゾーン分割でも使える形にする |
| 1-3 | `server.mts` | `perMessageDeflate` を試験的に有効化し、1-1/1-2との組み合わせで効果を測る |
| 1-4 | `protocol.mts`, `local-prediction.ts`, `src/net/` | `move` に `seq`、`state` に本人向け `ack`。予測を `online` でも有効化し、未確認入力の再適用で再調停。送信頻度を20〜30 Hzに統一 |
| 1-5 | `world3d.ts` | 他プレイヤー/動物を100 ms遅延のスナップショットバッファで線形補間 |
| 1-6 | `tests/` | 「5人・20人のスナップショット総量が閾値以下」「AOI外の個体が送られない」「`seq` の再調停で位置が収束する」の回帰テスト |
| 1-7 | 型 | `Room`/`Player` 型を `shared/types.mts` に追加し、strict対象を広げる |

### Phase 2: インターネット公開(1〜2か月)

ホスティングの比較:

| 案 | 概要 | 長所 | 短所 | 向く段階 |
| --- | --- | --- | --- | --- |
| 自宅ホスト+トンネル | Phase 0のNodeサーバーをCloudflare Tunnel / Tailscaleで公開 | コード変更ほぼゼロ、無料 | ホストPCが起動中のみ、上り回線に依存 | 「別の家の友達も」までの中間段階 |
| 小さなVPS/コンテナでNode | `server.mts` を常時稼働、前段で `wss://` を終端 | 最も単純、既存テストがそのまま効く | 費用と運用は自分 | 常設の公開サーバーの最初の形 |
| Cloudflare Durable Object | 既存 `cloudflare/` を拡張 | 運用レス、エッジ | `alarm()` 駆動とHibernatable WebSocketへの書き換え、1部屋固定の解消が必要 | 常時稼働不要・無料の要件が強い場合 |

推奨: 自宅ホスト+トンネル → VPS の順。Durable Objectは帯域削減後に人がいる間だけ tick する形へ書き換えてから再評価する。
