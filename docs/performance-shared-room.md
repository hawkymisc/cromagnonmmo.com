# 共有部屋を1人で遊ぶときの性能調査と改善候補

`pnpm run start:lan`（またはそのコンテナ）で開いた共有部屋に、1人だけで入って遊んでいる状態を対象に、処理が重くなりうる要因と改善候補を洗い出したものです。タイトルの「ひとりで遊ぶ」（ブラウザーのWorkerで動くソロ）は対象外です。計測の一般的な進め方は [性能の確認](performance.md)、通信方式の計画は [マルチプレイ化の設計レビューと計画](multiplayer-plan.md) を参照してください。

- 調査日: 2026-11-21 / 対象コミット: `d62bb7b`（実行系のソースは `b7d2192` から変更なし）
- きっかけ: tailnet内の別の機器から共有部屋に入って1人で遊んだとき、動きや処理が重いと感じる瞬間があった
- 調査時点の稼働構成: WindowsのPodman（WSLの仮想マシン、`--network host`）でコンテナを起動し、`tailscale serve --tcp` でtailnetに公開。ほかの機器は `http://<tailnetの名前>:3000`（平文のHTTP）で開く

**この文書の限界。** 重い瞬間そのものは再現・観測していません。以下は、コードの読解と、ブラウザーもネットワークも使わない机上の計測（[`scripts/benchmark-shared-room.mjs`](../scripts/benchmark-shared-room.mjs)）に基づく候補と予想です。どれが実際の原因かは「[最初に行う計測](#最初に行う計測)」で切り分けてください。効果の大小は予想であり、小さいと見積もった候補も除外していません。

この文書の単位は、KBが1,000バイト、KiB・MiBが1,024バイト・1,048,576バイトです。

## 要約

1. **サーバーの処理は原因ではありません（計測済み）。** 1人の部屋のtickは平均0.2 ms（50 msの枠の0.4%）、10秒ごとの自動保存の同期部分は0.5 ms未満です。
2. **平文のHTTPで開くと、ページは「安全でないコンテキスト」になります。** このとき、モデルの検証に使うSHA-256がブラウザー内蔵の実装（SubtleCrypto）ではなく、メインスレッドで動くJavaScriptの実装に切り替わります。4 MiBの検証で、メインスレッドをおよそ90 ms（5 msほどの区切りで）使います。SubtleCryptoなら約5 msで、メインスレッドを使いません。GLBは埋め込み画像をもう一度ハッシュし、その最初の区切りは最大で26 msほど途切れずに続きます。検証済みファイルの保存（CacheStorage）も使えないため、ページを開くたび、また解放したモデルを使い直すたびに、同じ検証をやり直します。新しい場所へ歩いてモデルが読み込まれる瞬間の引っかかりとして現れる、最も有力な候補です。ホストのPCで `localhost` を開いた場合や `https` では起きません。
3. **自分の移動に予測がありません。** 共有部屋（`online`）では、キーを押してから自分のキャラクターが動き出すまでに、設計上およそ100〜200 ms＋通信の往復時間がかかります。フレームレートが出ていても「動きが重い」と感じる要因です。予測の実装（`LocalPrediction`）は既にあり、展示用の `lan` モードでだけ有効です。
4. **1人でも毎秒約185 KB（約1.5 Mbps）を受信します。** 18.5 KBの状態フレームを毎秒10回、そのうち87%は敵34体の全項目です。tailnet（WireGuard）では1フレームが約16個のパケットに分かれ、1個でも遅れると後続のフレームがすべて待たされます（TCP）。`perMessageDeflate` を有効にするだけで約0.5 KB（−97%）になり、1パケットに収まります。
5. 描画側（30 fps固定、状態を受け取るたびのHUD更新、毎フレームのラベル更新、モデル受け入れ時のデコードやシェーダーのコンパイル）は、ソロと共通の負荷です。端末によって効き方が大きく変わるため、計測してから順位を見直します。

## 計測

`pnpm run build` のあと `node scripts/benchmark-shared-room.mjs 120` を実行した結果です（Node.js 26.13.1、Windows 11のデスクトップPC、`HOME` 部屋に `GameConnection` のダミーを1体接続、時計は擬似的に進める）。描画、GPU、実際のネットワーク遅延は含みません。走る経路は敵に近づかず、120秒の間に資源などの世界を含むフレームは出なかったため、戦闘・飛び道具・採集のフレームは測っていません。

### ページ自身のSHA-256（安全でないコンテキスト）

| 項目 | JavaScriptの実装（[`src/asset-hash.ts`](../src/asset-hash.ts)） | SubtleCrypto |
| --- | --- | --- |
| 4 MiBの検証で計算にかかる時間 | 約90 ms（約45 MiB/秒）。メインスレッド | 約5 ms。メインスレッドの外 |
| 途切れずにスレッドを占有する時間 | 256 KiBごとに平均5.4 ms（最大8.2 ms） | — |

256 KiBごとにタイマーで処理を譲るため、検証が終わるまでの時間はこれより長くなります（Windows上のNode.jsでは4 MiBで約250 ms。ブラウザーでの値は未計測）。スマートフォンでは計算そのものが数倍かかる見込みです。

配信するGLBは115個・85.2 MiB、最大3.9 MiBです（`dist/delivery/cache`）。GLBはファイル全体の検証（[`src/asset-download.ts`](../src/asset-download.ts)）のあと、埋め込み画像ごとにもう一度ハッシュを計算します（[`src/embedded-glb.ts`](../src/embedded-glb.ts) の `parseEmbeddedGLB`）。埋め込み画像はGLBのバイト数の58%（49.1 MiB）で、検証の仕事は約1.6倍になります。画像のハッシュは1つのGLBの全画像について同時に始まり、それぞれ最初の256 KiBまでを途切れずに計算するため、最初の区切りは中央値で286 KiB（約6 ms）、最大で1,205 KiB（約26 ms）になります。

## 入力から画面までの経路

共有部屋で自分のキャラクターを動かすとき、処理は次の順に進みます。括弧内は各段の待ち時間（平均／最大）です。

1. キーボードとゲームパッドの入力を70 msごとに読み取って `move` を送る — `setInterval(updateMovementInput, 70)`（35 ms／70 ms）。タッチは指が動くたびに読み取って送る
2. ブラウザー → tailnet → `tailscale serve` → WSL → コンテナのNode.js（往復時間の半分）
3. サーバーが次のtickで位置を進める — `setInterval(tick, 50)`（25 ms／50 ms）
4. 前回の送信から90 ms以上たったtickの終わりに、全員へ状態を送る — tickの2回に1回（25 ms／50 ms）
5. コンテナ → ブラウザー（往復時間の半分）
6. `JSON.parse` → `applyFrame` → `renderer.setState` → `updateHUD`（すべてメインスレッド）
7. 次の描画フレームで、モデルを最新の位置へ指数的に近づける — 30 fps固定、係数 `1 - exp(-dt * 20)`（17 ms／33 ms）

机上の合計は、動き出しまで平均およそ100 ms＋往復時間、最大およそ200 ms＋往復時間です。その後も表示位置は、サーバーの位置を50〜100 ms遅れで追いかけます。カメラは自分のモデルに追従するため、フレームの到着が乱れると画面全体の進み方が揺れます。ソロ（Worker）も同じ経路で、2と5がないだけです。

## 重くなりうる要因

### A. 安全でないコンテキスト（平文HTTP・`localhost` 以外）に固有のもの

| # | 要因 | 根拠 |
| --- | --- | --- |
| A1 | モデルの検証がメインスレッドのJavaScriptになる。256 KiBごとに約5.4 ms占有し、30 fpsの1フレーム（33 ms）の16%を使う。読み込みは同時に2件まで進む | `sha256()` は `crypto.subtle` がないとき自前の実装を使う（`src/asset-hash.ts`）。SubtleCryptoは安全なコンテキスト専用 |
| A2 | GLBの埋め込み画像を、ファイル全体の検証のあとにもう一度ハッシュする。仕事は約1.6倍になり、最初の区切りは最大26 msほど途切れない | `parseEmbeddedGLB` の `sha256(imageBytes(...))`。上の計測 |
| A3 | 検証済みファイルの保存（CacheStorage）が使えない。ブラウザーのHTTPキャッシュは効くので本体の取り直しは避けられるが、ページを開くたび、また解放したモデルを使い直すたびに、ホストへの問い合わせ1往復とハッシュのやり直しが要る | `createBrowserVerifiedAssetCache` は `isSecureContext !== true` で `null` を返す（`src/verified-asset-cache.ts`） |
| A4 | 識別子がECDSAの鍵ではなくランダムな秘密になる。性能への影響はないが、URLを `https` に変えると別の人物として扱われる | `src/net/identity.ts` |

### B. 通信と同期

| # | 要因 | 根拠 |
| --- | --- | --- |
| B1 | 自分の移動に予測がない | `renderer.prediction.enabled = multiplayer.mode === 'lan'`（`src/main.ts`）。LANホストの設定は `mode: 'online'` |
| B2 | キーボードとゲームパッドの入力の読み取りが70 ms間隔 | `setInterval(updateMovementInput, 70)`（`src/main.ts`） |
| B3 | 状態の送信が約10 Hzで、tickの2回に1回 | `now - room.lastBroadcast >= 90`（`application/game-core.mts` の `tick`） |
| B4 | 全個体の全項目をJSONで毎回送る（世界の項目だけは変化したときのみ）。1人でも185 KB/秒 | `application/snapshot.mts`。上の計測 |
| B5 | 圧縮なし | `perMessageDeflate: false`（`server.mts`） |
| B6 | 興味領域がない。到着地点から霧の届く距離（118 m）以内にいる敵は34体中3体だけだが、全員を常に受け取る | `snapshot()` は部屋の全個体を送る。上の計測 |
| B7 | TCPの1本の流れに16パケットのフレームを流すため、1個の遅れが後続のフレームをすべて待たせる | WebSocket。Wi-Fiや中継経路で起きやすい |
| B8 | 送信が詰まったとき、Node.js側に512 KiB（現状の約2.8秒ぶん）たまるまで古いフレームを積み続ける。OSの送信バッファーと `tailscale serve` の中継がその手前にあるため、実際に滞留する量はこれより多くなりうる | `socket.bufferedAmount < 512 * 1024`（`game-core.mts` の `send` と `broadcast`） |
| B9 | 受信側に補間用のバッファーがない。届いた最新の位置へ指数的に寄せるため、到着間隔の揺れがそのまま速度の揺れになる | `src/world3d.ts` の `renderWorld` |
| B10 | 届いたフレームを1件ずつ同期的に処理する。詰まりが解けて数件まとめて届くと、その回数だけ `setState` と `updateHUD` が走る | `src/main.ts` の `message` リスナー |
| B11 | 経路の段数が多い（WireGuard → `tailscale serve` のTCP中継 → WSL → コンテナ）。直結ではなく中継サーバー（DERP）経由になると、往復時間と揺れが大きく増える | 稼働構成。`tailscale status` で `direct` か `relay` かを確認できる |
| B12 | タッチ操作では、指が動くたびに `move` を送る。共有部屋ではこの送信に間隔の上限がないため、サーバーの受け付け上限（70個、毎秒35個補充）を超えると、攻撃や停止を含むコマンドが黙って捨てられうる。指の動きの頻度は未計測 | `src/touch-controls.ts` の `hooks.move()` → `updateMovementInput`。`src/main.ts` の送信条件、`game-core.mts` の `handleCommand` |

### C. 状態を受け取るたびにメインスレッドで行う仕事（10 Hz）

| # | 要因 | 根拠 |
| --- | --- | --- |
| C1 | `updateHUD()` が毎回、ミニマップの再描画、`nearby()`（資源77か所の走査と衝突判定）、プロフィールカードと狩りのHUDの更新を行う。メニューの更新は、開いていなければすぐ戻る | `src/main.ts` の `updateHUD` |
| C2 | これとは別に `setInterval(updateHuntingHUD, 100)` が10 Hzで走り、`updateHUD` からも呼ばれる | `src/main.ts` |
| C3 | `player()` が呼ばれるたびに `state.players.find`。1回の受信で数十回 | `src/main.ts` |
| C4 | `renderer.setState` が毎回 `syncEnemies` と `updateActorResidency` を実行（後者は毎フレームも実行） | `src/world3d.ts` |
| C5 | `applyFrame` が毎回オブジェクトを作り直し、世界を含むフレームでは資源の配列が新しくなるため `syncResources` が全件を回す | `src/net/state-store.ts`、`src/world3d.ts` |

| # | 要因 | 根拠 |

### E. モデルが読み込まれる瞬間（歩いて新しい場所に入ったとき）

| # | 要因 | 根拠 |
| --- | --- | --- |
| E1 | GLBの解析とmeshoptの展開がメインスレッド | `GLTFLoader.parseAsync`、`MeshoptDecoder`（Workerを使っていない） |
| E2 | テクスチャーのGPUへの転送とミップマップ生成が、初めて描く瞬間に同期的に起きる。圧縮テクスチャー（KTX2）は使っていない | `src/embedded-glb.ts` |
| E3 | 到着地点のシェーダーは入場前にコンパイル済みだが、あとから読み込まれるモデル（別の地域の地形・名所・敵など）のマテリアルは、初めて描く瞬間にコンパイルする | 事前のコンパイル（`compileScene`）は `prepareEntry`・待合の洞窟・カメラのフェードでのみ呼ばれる |

| # | 要因 | 根拠 |
| --- | --- | --- |

## 改善候補（予想される効果の大きい順）

P01の注意:

- tailnetでMagicDNSとHTTPS証明書を有効にする必要があります。
- WebSocketの接続は、ページの `Origin` と要求の `Host` が一致するときだけ受け付けます（`server.mts` の `sameHost`）。`tailscale serve` のHTTPSの中継を経由しても一致するかは未確認です。TLSだけを終端してTCPを中継する形（`--tls-terminated-tcp`）なら、HTTPの内容はそのまま届く見込みです（未確認）。
- URLが変わると、ブラウザーの保存領域が別になります。識別子と再開用の合言葉が引き継がれないため、部屋に残っている人物は別人として扱われます。引き継ぎの手順を先に決めてください。
- 招待リンクとQRコードは、招待を開いたページのアドレスから作ります。`https` で開いた機器が出す招待は `https` になります。ホストが `localhost` で開いた場合はホストのネットワークアドレスに置き換えますが、コンテナの中では仮想マシンのアドレスになります。
- `https` では、タイトルに「ひとりで遊ぶ」も表示されるようになります。
- 原因の確認だけなら、Chromeの `chrome://flags/#unsafely-treat-insecure-origin-as-secure` に平文のアドレスを登録して比べる方法があります。

P02の注意:

- 共有部屋では、`updateMovementInput` を呼ぶたびに `move` を送ります（`src/main.ts` の送信条件は、`online` では間隔を見ません）。呼び出しを毎フレームにするだけでは、サーバーの受け付け上限（毎秒35個補充）を数秒で使い切り、以後のコマンドが捨てられます。読み取りと送信を分け、送信に間隔の上限を設けてください。
- `LocalPrediction.step` は、状態が250 ms届かないと動きを止めます。通信が詰まったとき（B7）には予測も止まるため、P03と合わせて行うと確かです。
- `move` に連番、`state` に確認応答を入れる（計画1-4）と、再調停が確かになります。

P04の注意:

- 埋め込み画像のハッシュは、別々のファイル（モデルとそのLOD）の間で同じテクスチャーを共有するための識別子です（`coalesceTextures`、`textureIdentity`）。ファイルごとの位置に置き換えると共有が止まり、テクスチャーのメモリーが増えます。内容に基づく識別子のまま、計算の場所だけを変えてください。
- 安全でないコンテキストでは、Workerの中にもSubtleCryptoがありません。同じJavaScriptの実装を、メインスレッドの外で動かすことになります。

## 組み合わせと順序

- **P01とP04は、同じ問題の設定側とコード側の対策です。** P01は自分のtailnetで今すぐ試せます。P04は、`https` を用意できないLAN（IPアドレスで開くスマートフォン）を含めて直します。両方行っても無駄にはなりません。
- **P03 (a) は最初に試す価値があります。** 1行の変更で、帯域の問題（B4〜B7）のほとんどが片づきます。`ws` の圧縮は接続ごとにメモリーを持つため、数十人の部屋では同時に圧縮する数とメモリーを確認してください。8人までの部屋では問題になりません。
- **P03 (b) は「変化した個体を丸ごと」では足りません。** 丸ごとでは−43%にとどまります。項目単位にするか、変わらない項目（名前・モデル・大きさ・最大体力など）を初回だけ送る形にします。(a) のあとの (b) は、帯域ではなく、ページが毎回18 KBを解析して全個体を作り直す仕事（C4、C5）を減らすために行います。(c) とP19を加えると、変化する個体そのものが減ります。
- **P02はP03・P06と組にします。** 予測は状態が250 ms途切れると止まるため、通信の揺れを先に小さくします。入力を毎フレーム読むなら、送信の上限（P06）が前提です。
- **P02の前後でP11の価値が変わります。** 予測を入れると、送受信の拍をそろえる効果は自分の動きには現れにくくなり、他人の動きにだけ残ります。
- **P03のあとでP05・P07・P13が効きます。** フレームが1パケットに収まると遅延の揺れが小さくなり、補間用のバッファーを短く（100 msより短く）できます。
- **小さい候補が次のボトルネックになる順。** 通信（B）と読み込み（A、E）を片づけると、残るのはメインスレッドの定常負荷（C、D）です。そのときはP10 → P14 → P16 → P17の順に、プロファイルで大きいものから着手します。60 fps（P12）を選べるようにすると、1フレームの予算が33 msから16 msになるため、これらの小さい候補の重みが倍になります。
- **人数が増えるとFが上がってきます。** 8人の家庭内LANでは問題になりませんが、計画のPhase 2以降（数十人）ではP24〜P26が必要です。

## 検討して採らなかった見方

- **サーバーのtickや自動保存が重い。** 計測で否定しました（tick平均0.2 ms、保存の同期部分0.5 ms未満）。ただし、tickの「間隔」の揺れ（イベントループの遅れ、仮想マシンの時計）は机上では測れないため、P27・M9で確認します。
- **状態フレームの `JSON.parse` が重い。** 18 KBの解析はV8で0.02 msでした。受信の負荷は解析ではなく、そのあとの `setState` と `updateHUD` の側にあります。
- **「変化した個体だけ送る」で十分。** 待機中でも敵の半分が毎フレーム変化するため、個体単位の差分では半分しか減りません。
- **帯域を減らすには差分配信が要る。** 全量のままでも、前のメッセージを辞書に使う圧縮で−97%になります。差分配信の目的は、帯域よりもページとサーバーの仕事の削減です。
- **数値の丸めで大きく減る。** −8%にとどまりました。
- **平文HTTPでは毎回モデルをダウンロードし直す。** HTTPキャッシュが効くため、取り直すのは問い合わせの1往復だけです。重いのは検証のやり直しです。
